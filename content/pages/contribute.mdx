The catalog is a set of plain YAML files in a Git repository. Every change — a new entry, a correction, a policy revision — is a pull request that anyone can read, and every pull request is checked by the same validation the site uses to build.

<h2 id="corrections">Report a correction</h2>

If something is wrong or out of date, the most useful report includes the entry, the specific statement, and a source that supports the correction (an official page, license file, model card, repository, or filing). Each entry page has **Report a correction** and **Edit this entry** actions that open the right issue form or file once the repository is configured. Corrections are handled the same way for everyone, including listed organizations. You can also email a correction; no GitHub account is needed. Corrections are reviewed as time allows, and USASI does not promise a response time. Accepted corrections are made in the open and recorded in the [changelog](/changelog/).

<h2 id="new-entries">Suggest a new entry</h2>

Use the entry-request issue form, or open a pull request with a new record. Before suggesting an entry, check the [eligibility policy](/methodology/#eligibility): the entry needs a documented U.S. basis, and for projects that basis is the governing or maintaining entity, not the contributors. Requests that cannot yet be verified are kept in the internal review queue (`CONTENT_REVIEW.md`) rather than published.

<h2 id="workflow">Editing workflow</h2>

1. Fork the repository and create a branch.
2. Add or edit a file in `content/organizations/` or `content/artifacts/`. The file name must match the record's `slug`. The full field reference is in `docs/CONTENT_FORMAT.md`.
3. Cite a source for every statement. Only cite pages you have opened and read, and record the date you read them in `accessed_at`.
4. Set `last_reviewed` to today only if you checked the entry's evidence. Set `updated_at` to today for any substantive edit. Never change `released_at` without a source.
5. Run `npm run validate`. It checks schemas, unique slugs and source IDs, relationships between records, source references, eligibility and publication consistency, dates, family and release structure, and placeholder text.
6. Open a pull request using the template. A maintainer reviews the evidence before merging.

<h2 id="evidence">Evidence requirements</h2>

- Licenses come from the license file or the model or dataset card, not from a summary on another site.
- Headquarters come from the organization's own pages or, for public companies, regulatory filings.
- News reporting is acceptable only for the specific claim it supports, and is labeled as a news report.
- Do not add funding, valuations, staff counts, user counts, benchmark scores, hardware requirements, or power figures unless the catalog's rules for that field are met. Most of these are not published at all.
- If a fact is unknown, leave it unknown.

The openness tier is never written by hand: the site computes it from the checklist and licenses using the published rubric.

<h2 id="policy-changes">Changing the rules</h2>

Changes to the eligibility policy, the openness rubric, or the [USASI Compact](/compact/) are proposed the same way, by pull request, and must update `ELIGIBILITY.md`, `OPENNESS.md`, or the Compact together with the code that applies them. Rubric changes get a new version number and a changelog entry.

<h2 id="code">Code contributions</h2>

The site is Next.js with TypeScript, Tailwind CSS, and Zod, exported as static files. Run `npm run typecheck`, `npm run lint`, `npm test`, and `npm run test:e2e` before opening a pull request. The README describes local development and deployment.
